# 90-01. 移行方針

## 1. 基本方針: ビッグバン移行ではなく「歩く骨格(Walking Skeleton)」から

全機能を一気に移植すると、動くようになるまで長期間フィードバックが得られず、
アーキテクチャの誤りに気づくのが遅れるリスクが高い。そのため以下の順序で進める。

1. **歩く骨格を先に通す**: ボリビア1ヶ国・英語のみ・最小限の機能(セットアップ→ダイス→移動→
   クイズマス着地→正誤判定→プレイヤーパネル更新)を、Domain→Application→Infrastructure→
   Presentation→テスト(Unit+E2E)まで全層通して動かす。ここでアーキテクチャの妥当性を検証する。
2. **機能を垂直スライスで追加**: 都市停車(購入/増資/売却/独占)、屋台/アイテム、季節イベント、
   厄災の神、CPU、セーブ/ロード、多言語、日本パック…の順に、1機能ずつ全層を貫通させて追加する。
3. **最後に演出・音声・パフォーマンスを仕上げる**。

この順序は [WBS](./02-wbs.md) のフェーズ構成に対応している。

## 2. 新旧の共存方法

- 現行 `grand-express.html` は `legacy/grand-express.html` としてリポジトリに残し、
  **移行完了まで「正しい挙動の一次情報(仕様書代わり)」として扱う**。
- 挙動に疑義が生じた場合は、必ず `legacy/` 版を実際に動かして確認し、Domain層のテストケースに
  落とし込んでから実装する。
- 新アプリと旧アプリのセーブデータ互換性は [ADR-0005](../10-architecture/04-adr/0005-persistence-and-save-format.md)
  の方針(スキーマ検証+マイグレーション関数)で担保する。完全互換が難しい場合は「旧セーブは
  読み込めるが、以後は新形式で保存される」形でよい(ユーザー合意の上)。

## 3. リスクと軽減策

| リスク | 影響 | 軽減策 |
|---|---|---|
| 中間マス生成アルゴリズム(`h32` ハッシュによる疑似乱数)の再現漏れ | 路線上のクイズ/青/赤/カードマスの配置が変わり、既存セーブと盤面がズレる | アルゴリズムをそのまま移植し、同一シードで同一盤面が生成されることをユニットテストで固定する(スナップショットテスト) |
| CPU AIの微妙な挙動差 | プレイ感が変わったと感じられる | `CPU` パラメータ表(acc/keep/invest/noise/item)をそのまま移植し、Domainテストで再現度を確認 |
| 71問のクイズ・18種のアイテム・季節文言など大量コンテンツの転記ミス | 誤字・データ不整合 | 手動転記せず、変換スクリプトで機械的に抽出・JSON化する([ADR-0007](../10-architecture/04-adr/0007-content-data-as-json.md)) |
| 翻訳文言の抜け漏れ | 一部言語だけ文言が欠ける | 4言語すべてに対応するJSONキーが揃っているかをビルド時テストで検証 |
| 音声(Web Audio)の完全再現 | 音楽的な再現には工数がかかる | 優先度を下げ、Phase 8(仕上げ)に配置。基本的なSE/BGM切り替えの疎通のみ先に確保する |
| SVGアニメーション(ダイス3D・カメラ追尾)の見た目差異 | 体験の質が変わる | E2Eでの自動検証は「動作する」ことのみとし、見た目の細部は手動QAでカバー |
| 移行途中でのスコープ肥大化 | 進捗が止まる | WBSの各フェーズごとに「完了の定義」を明確にし、フェーズ内で仕様追加をしない |

## 4. 全体の完了の定義(Definition of Done)

- 現行 `grand-express.html` の全機能(2ヶ国・4言語・全アイテム/クイズ/季節イベント/厄災効果)が
  新アプリで再現できている
- Domain/Application層のユニットテストがカバレッジ目標([テスト戦略](../20-testing/01-testing-strategy-tdd.md))を満たしている
- E2Eのクリティカルユーザージャーニーがすべてグリーン
- `legacy/grand-express.html` を参照しなくても新規機能追加ができる状態(=ドキュメントとテストが仕様として機能している)
- 本番相当環境(Vercel等)にデプロイ済みで、旧HTMLの提供は停止(またはアーカイブ)している
