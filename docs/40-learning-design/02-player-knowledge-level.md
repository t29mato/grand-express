# 40-02. プレイヤーごとの知識レベル

## 1. 背景

本作は同一画面で2〜4人が交代しながらプレイする。想定される主な遊び方は
**国際色豊かなメンバーが集まって一緒に遊ぶ** ケースであり、このとき対象国に対する
前提知識がプレイヤー間で極端に偏る。

- ボリビアパックをボリビア出身者と遊ぶ → その人はクイズをほぼ全問正解する
- 同じ卓の初見のプレイヤーは3択を当てずっぽうで選ぶ（期待正答率33%）

この状態は2つの意味で悪い。

1. **競技として壊れている。** クイズは1回あたり最大320の増減があり、勝敗を左右する。
   知識差がそのまま資産差になり、勝負にならない。
2. **学習として機能していない。** 出身者は既に知っていることを答えるだけで学びがなく、
   初見のプレイヤーは当てずっぽうなので記憶に残らない。**当てずっぽうの正解は学習では
   ない。**

そこで **プレイヤーごとに「対象国への知識レベル」を3段階で選べるようにする。**

## 2. 設計判断

### 2-1. 知識レベルは「プレイヤーの属性」ではなく「セッションの設定」である

ボリビア出身者は **ボリビアパックでは詳しいが、日本パックでは初見** である。つまり
知識レベルは（プレイヤー × 対象国）で決まる値であり、プレイヤーに永続的にひも付く
属性ではない。

1ゲーム＝1ヶ国なので、**ゲーム開始時のセットアップ画面で毎回選び、セッション内でのみ
保持する** のが正しい。プロフィールとして永続化しない。

### 2-2. ハンデはクイズにのみ適用する

物件の収入・到着賞金・厄災など、**対象国の知識と無関係な要素にはハンデをかけない。**
知識差が生む不公平はクイズに由来するので、補正もクイズに閉じるのが筋であり、
ゲームバランスへの副作用も最小になる。

### 2-3. CPUには不要

CPUの正答率は `src/domain/cpu/cpu-level.ts` の `CPU_TUNING.accuracy`
（gentle 0.45 / normal 0.65 / merciless 0.88）が既に同じ役割を果たしている。
知識レベルの選択UIは **人間スロットにのみ表示する。**

## 3. 3段階の定義

| レベル | 識別子 | 表示（案・ja） | 想定 |
|---|---|---|---|
| 初級 | `newcomer` | この国は初めて | 対象国の知識がほぼない |
| 中級 | `familiar` | すこし知っている | 既定値。旅行したことがある程度 |
| 上級 | `local` | よく知っている | 出身者・在住者・その国に詳しい人 |

既定値は `familiar` とし、何も触らなければ現状と同じ挙動になるようにする。

## 4. レベルが変えるもの

### 4-1. 採用案

| | 選択肢の数 | 正解時の賞金 | 不正解時の損失 |
|---|---|---|---|
| `newcomer` | **3 → 2**（誤答を1つ伏せる） | ×1.5 | ×0.5 |
| `familiar` | 3（現状） | ×1.0 | ×1.0 |
| `local` | 3（現状） | ×0.75 | ×1.5 |

考え方は囲碁の置き石と同じで、**知っている人ほど「当てて当たり前」なので取り分を減らし、
外したときの責任を重くする。** これにより、知識で劣るプレイヤーにも勝ち筋が残る。

倍率は既存の `Money.multiply()`（`src/domain/shared-kernel/money.ts`）で表現できる。
`Money.of` が `Math.round` するため、端数処理は値オブジェクト側で既に担保されている。

### 4-2. 「選択肢を2つに減らす」ことの是非

トレードオフがあるので明記しておく。

- **短所:** 当てずっぽうの成功率が33%→50%に上がる。当てずっぽうの正解は学習ではない。
- **長所:** 選択肢が減ると比較対象が絞られ、**「どちらだったか」を考える負荷が適正化されて
  記憶に残りやすい。** また、初見のプレイヤーが毎回損をして早々に脱落する
  （＝それ以上学ばなくなる）事態を防げる。

初見プレイヤーが3択で連敗し続けて興味を失う方が損失が大きいため、**採用する。**
ただし伏せるのは必ず誤答であり、正解を伏せてはならない。

実装上は、`UiState` の `quiz` が既に `optionOrder: readonly number[]` を持っており
（`game-store-types.ts`）、`quiz-modal.tsx` はこの配列をそのまま描画している。
**短い `optionOrder` を渡すだけで2択になる** ため、モーダル側の変更は不要。

### 4-3. 結果表示は全レベル共通

[40-01](./01-quiz-as-learning-device.md) の案1（クイズ結果モーダル）は、レベルに関係なく
**必ず正解と解説を表示する。** ハンデは金額の話であって、学習機会を削ってはならない。

`local` のプレイヤーが間違えた問題は、その卓で最も価値の高い学習素材になる。終了時の
おさらい画面は、**詳しい人がその場で解説役になる**きっかけとしても機能する。

## 5. 実装方針

### 5-1. ドメイン層

`src/domain/quiz/knowledge-level.ts` を新設する。**`src/domain/cpu/cpu-level.ts` と
同じ構造にそろえる**（型 + チューニング表の定数）。

```ts
export type KnowledgeLevel = "newcomer" | "familiar" | "local";

export interface KnowledgeTuning {
  /** 提示する選択肢の数。実際の選択肢数を超える場合は全件提示。 */
  readonly visibleOptionCount: number;
  /** 正解時の賞金倍率。 */
  readonly winMultiplier: number;
  /** 不正解時の損失倍率。 */
  readonly loseMultiplier: number;
}

export const KNOWLEDGE_TUNING: Readonly<Record<KnowledgeLevel, KnowledgeTuning>> = {
  newcomer:  { visibleOptionCount: 2, winMultiplier: 1.5,  loseMultiplier: 0.5 },
  familiar:  { visibleOptionCount: 3, winMultiplier: 1.0,  loseMultiplier: 1.0 },
  local:     { visibleOptionCount: 3, winMultiplier: 0.75, loseMultiplier: 1.5 },
};
```

- `Player`（`src/domain/player/player.ts`）に `knowledgeLevel?: KnowledgeLevel` を追加し、
  `createPlayer` の引数にも通す。`cpuLevel` と同じ扱いにする。
- `gradeAnswer`（`src/domain/quiz/quiz-grading-service.ts`）に `KnowledgeLevel` を渡し、
  `QUIZ_TIER_REWARDS` の額に倍率を適用する。

### 5-2. アプリケーション層

- `PlayerSetup`（`start-game.use-case.ts`）に `knowledgeLevel` を追加する。
  **`cpuLevel` がゲーム全体で1つなのに対し、`knowledgeLevel` はプレイヤーごと** である点に注意。
- `answerQuiz`（`answer-quiz.use-case.ts`）は `player.knowledgeLevel` を `gradeAnswer` に渡す。

### 5-3. プレゼンテーション層

- `game-store-turn-flow.ts` の出題時、`shuffledIndexes()` の結果を
  `visibleOptionCount` 件に絞る。**正解のインデックスが必ず含まれるように**、
  正解を1つ確保してから残りを誤答からランダムに詰め、最後に並びをシャッフルする。
- `setup-screen.tsx` のプレイヤー行に、既存の `.seg`（3ボタン）と同じ形で知識レベルの
  セグメントを追加する。`slot.mode === "human"` のときだけ表示する。
- i18n（`src/i18n/messages/{en,es,fr,ja}.json`）に4キー追加:
  見出し1つ＋レベル名3つ。

### 5-4. セーブ形式への影響

`Player` にフィールドが増えるため、**ADR 0005 のセーブ形式が変わる。** 既存のセーブデータ
（`localStorage` / Base64共有コード）には `knowledgeLevel` が存在しないので、
**読み込み時に未指定なら `familiar` を既定とする** 後方互換の分岐を入れること。
`docs/10-architecture/04-adr/0005-persistence-and-save-format.md` に追記する。

## 6. UI上の懸念

プレイヤー行は現在「名前入力 + 3ボタンのセグメント」で構成されており、ここに
もう1つ3ボタンのセグメントを足すと **狭い画面で横に収まらない可能性が高い。**
実装時に4人分を並べた状態でモバイル幅を確認し、必要なら行を2段に折り返す。

レベル名は短い語を選ぶこと（例: 日本語なら「初/中/上」ではなく意味の伝わる短語）。
4言語すべてでセグメントに収まる長さかを確認する。

## 7. 未解決の論点

- **知識レベルの自己申告は正確か。** 遠慮して低く申告する人、見栄で高く申告する人が
  いる。正答率の実績から自動調整する案もあり得るが、1ゲームのサンプル数では統計的に
  無意味なので、**当面は自己申告のままとする。**
- **`local` のプレイヤーにとっての学習価値。** ハンデは競技バランスを直すだけで、
  上級者に新しい学びを与えない。ここを本当に解決するのは
  [40-01](./01-quiz-as-learning-device.md) の将来課題である「問題側への `difficulty`
  付与と出し分け」であり、知識レベルはその難易度選択の入力としても再利用できる。
