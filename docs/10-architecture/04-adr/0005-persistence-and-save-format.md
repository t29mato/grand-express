# ADR-0005: セーブ形式は localStorage + 共有コードを踏襲し、スキーマ検証とバージョニングを追加する

- ステータス: 承認
- 日付: 2026-08-05

## コンテキスト

現行実装は `localStorage` へのJSON保存と、Base64エンコードした「共有コード」を手動でコピー&ペーストする
方式(`snapshot`, `writeSave`, `readSave`, `encode`, `decode`)で永続化している。サーバーは存在しない。
この方式自体はシンプルで有効だが、以下の弱点がある。

- 保存データの形状に対するバリデーションがなく、壊れた/古い形式のコードを読み込むと例外で落ちる
  (現行は `try/catch` で `badCode` アラートを出すのみで、部分的に壊れたデータはすり抜ける可能性がある)
- スキーマバージョンの概念がなく(`v:4` というフィールドはあるが読み込み時に使われていない)、
  将来ドメインモデルを拡張した際に旧セーブとの互換性を壊しやすい

## 決定

- 永続化方式そのもの(`localStorage` + Base64共有コード)は踏襲する。サーバー保存は現時点で不要。
- `application/ports/game-repository.ts` というポートを定義し、`infrastructure/persistence/local-storage-game-repository.ts`
  で実装する。
- セーブデータは `zod` スキーマ(`SaveSchemaV1` など)で厳格に検証し、検証に失敗した場合は
  ドメイン層に到達させずアプリケーション層で明示的なエラー(`InvalidSaveDataError`)として扱う。
- スキーマバージョンフィールドを正式に使用し、将来のフィールド追加・変更時は
  `infrastructure/persistence/migrations/` にマイグレーション関数を追加する方針とする。

## 代替案

- **IndexedDB化**: 保存できるデータ量は増えるが、本アプリの1セーブあたりのデータ量は小さく
  (プレイヤー数×物件数程度)、localStorageで十分。オーバーエンジニアリングのため不採用。
- **サーバー保存**: 将来のオンライン対戦機能と合わせて検討する余地はあるが、今回のスコープ外。

## 影響

- 旧HTML版で作成された共有コードとの互換性は「読み込み時にスキーマ検証し、旧バージョンはマイグレーション関数を
  通す」ことで担保する。マイグレーション関数を用意しない場合は非互換として明示的にエラーメッセージを出す
  (現行のように無言で壊れることを防ぐ)。
