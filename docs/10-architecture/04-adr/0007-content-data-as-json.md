# ADR-0007: ゲームコンテンツ(都市・クイズ・アイテム・季節・厄災テーブル)はコードから分離しJSON化する

- ステータス: 承認(2026-08-05実装。ADR-0006と合わせて実用簡略化あり、下部追記参照)
- 日付: 2026-08-05

## コンテキスト

現行ファイルの肥大化の最大要因は、`BOLIVIA` と `JAPAN` の2つの国データオブジェクトである
(都市約30件×2ヶ国、クイズ71問、アイテム18種、季節イベント12ヶ月分、厄災テーブル)。これらは
**コードではなくマスターデータ**であり、コードと同居させる必然性がない。ユーザーの課題意識である
「1ファイルあたりのLLMトークン消費が大きい」を最も直接的に解決できる箇所でもある。

## 決定

- 国コンテンツは `infrastructure/content/{country}.json` として、コードから完全に分離する。
- Domain層は `CountryContentPack` という型(スキーマ)だけを定義し、実データには一切依存しない。
- `CountryContentRepository`(ポート)経由でJSONを読み込み、`zod` スキーマで検証してから
  Domain層の型にマッピングする。壊れたコンテンツデータ(存在しない都市IDへのedge参照など)は
  起動時/ビルド時に検出する(現行は不整合があっても実行時までわからない)。
- 翻訳文言は [ADR-0006](./0006-i18n-strategy.md) の方針でロケール別ファイルに分離するため、
  `content/{country}.json` には言語非依存の数値データ(座標・コスト・収入等)とID参照のみを持たせる。

## 代替案

- **コード内オブジェクトのまま型だけ付ける**: ファイルサイズの問題(LLMトークン消費)が解決しないため
  今回の目的に対して不十分。
- **CMS/データベース化**: 更新頻度・チーム規模に対してオーバーエンジニアリング。静的JSONで十分。

## 影響

- 移行時、現行コード内の `C()`, `Q()`, `IT()` ヘルパーで組み立てられているデータを抽出し、
  スキーマに沿ったJSONへ変換する一括変換スクリプトを書く(手動転記によるヒューマンエラーを防ぐため)。
- コンテンツの整合性(edgeが参照する都市IDが実在するか、クイズの選択肢数など)は
  ビルド時テスト(スキーマ+参照整合性チェック)で担保する([テスト戦略](../../20-testing/01-testing-strategy-tdd.md) 参照)。

## 実装時の追記(2026-08-05, Phase3実施時)

抽出は `scripts/extract-legacy-content.mjs` で機械的に行った(legacy側の純粋データ定義部分を
Node上で直接requireし、手動転記を排除)。当初案では「翻訳文言は言語非依存のコンテンツJSONから
完全に分離する」としていたが、実装では **翻訳文字列を `{en,es,fr,ja}` のままコンテンツJSONに
インラインで残す**簡略化を採った(理由は [ADR-0006の追記](./0006-i18n-strategy.md#実装時の追記2026-08-05-phase6実施時)
と同じ: next-intlのロケール別ファイル分離まではせず、実用上のスコープ調整)。

これにより「コードとコンテンツデータの分離」という当初の主目的(LLMトークン消費削減)は
達成しつつ(`bolivia.content.json` / `japan.content.json` として各国 約185KB のデータファイルに
分離済み)、「コンテンツと翻訳文字列の分離」は見送っている。将来的に翻訳フローを本格運用する
場合(翻訳者への外部委託等)は、この2つのJSONをさらに `content/{country}.json`(数値データ)と
`content/{country}/{locale}.json`(文言)に分割するのが望ましい。
