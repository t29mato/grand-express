# 00. 現状分析

## 1. これは何か

`grand-express.html` は鉄道すごろく型のボードゲームです。プレイヤー(人間/CPU、2〜4人)が
サイコロを振って国内の路線を進み、都市に停まって物件(ビジネス)を購入・増資・売却し、
目的地に一番乗りすると賞金を得る、という双六型のパーティゲームです。

- 収録国: ボリビア(Bolivia)・日本(Japan)の2パック、各国 約30都市
- 対応言語: 英語 / スペイン語 / フランス語 / 日本語(4言語、パイプ区切り文字列で埋め込み)
- クイズ: 71問(路線上のマスに停まると出題)
- アイテム: 18種(移動系・先制効果系・パッシブ系)
- 季節イベント: 12ヶ月分、地方ごとの収入補正
- 「厄災の神(Misfortune Spirit)」: 最下位プレイヤーに憑依し、ランダムな不利益(物件喪失・他プレイヤーへの送金・強制移動・アイテム/現金強奪)を与える。他プレイヤーとすれ違うと憑依先を移せる。
- 保存: `localStorage` + Base64エンコードした共有コードによる手動セーブ/ロード
- 描画: SVGを `document.createElementNS` で手動生成、カメラのパン/ズーム/追尾、3Dダイスのアニメーション
- 音声: Web Audio API による手書きのプロシージャル音楽・効果音(地方ごとに曲調が変化)

## 2. 技術構成(現状)

| 項目 | 現状 |
|---|---|
| ファイル数 | 1ファイル(`grand-express.html`) |
| 行数 / サイズ | 約2,964行 / 約385KB |
| 型システム | なし(素のJavaScript) |
| 状態管理 | モジュールスコープの `let`/`const` グローバル変数(`players`, `turnIdx`, `month`, `dest`, `spiritHolder` …) |
| 描画 | 直接 DOM / SVG API 呼び出し、`innerHTML` によるモーダル組み立て |
| 永続化 | `localStorage` への `JSON.stringify` 保存、Base64共有コード |
| 国際化 | 独自フォーマット `"英|西|仏|日"` を `_t()` でパースし `tx()` で現在言語を取り出す |
| コンテンツデータ | 都市・クイズ・アイテム・季節イベント・厄災テーブルがすべてコード内にリテラルで記述 |
| テスト | なし |
| ビルド | なし(ブラウザがそのまま解釈) |

## 3. 抽出できた主なドメイン概念

コードを読み解いた結果、以下の概念が識別できました(詳細は [ドメインモデル](./10-architecture/02-domain-model-ddd.md) 参照)。

- **Country / City / Edge / Node**: 国データ、都市、路線、路線上の中間マス(クイズ/青/赤/カード)
- **Player**: 現金・所持アイテム・所有物件・現在位置
- **Property(Business)**: 都市ごとに複数存在。コスト・収入・レベル(1〜5)・独占判定
- **Item**: 移動系(`move`)・先制系(`pre`)・パッシブ系(`passive`)の3種
- **QuizQuestion**: 難易度ティア(low/mid/high)ごとに勝敗時の増減額が異なる
- **SeasonalEvent**: 月ごとに地方収入補正(`mod[region]`)を変化させる
- **MisfortuneSpirit(厄災の神)**: 保有者・強さレベル・残りターン数、発動時の4種類の災難(物件喪失/送金/瞬間移動/強奪)
- **GameSession**: 通貨単位・カレンダー(月/年)・目的地・賞金額(月が進むほど増加)・ターン進行・勝敗判定
- **CPU戦略**: 3段階の難易度ごとに正答率・アイテム使用確率・投資積極性などのパラメータが異なる自動意思決定

## 4. 課題(Pain Points)

1. **保守性が低い**: ゲームルール・描画・DOM操作・音声・翻訳・永続化・コンテンツデータがすべて同じスコープに混在しており、1つの変更が広範囲に影響しやすい。
2. **LLMのトークン消費が過大**: 1ファイル385KBのため、LLMに小さな修正を依頼する場合でもファイル全体(またはその大部分)を読ませる必要があり、コストと応答時間の両方を圧迫している。
3. **テストが皆無**: 経済計算(収入・独占倍率・売却額)やターン進行のロジックにテストがなく、リグレッションを検出できない。
4. **型がない**: `players`, `G.cities` などのオブジェクト形状が暗黙的で、リファクタリング時に壊れやすい。
5. **グローバル変数による状態管理**: `let players, turnIdx, month, dest, spiritHolder ...` が多数のトップレベル変数として存在し、状態遷移の全体像を追いにくい。
6. **コンテンツとコードの同居**: 都市・クイズ・アイテムのデータ量がファイル肥大化の主要因(BOLIVIA/JAPANの2ブロックだけで全体の半分近くを占める)。
7. **翻訳文字列の保守性**: パイプ区切り文字列 (`"en|es|fr|ja"`) は差分レビューがしづらく、キー抜けの検出もできない。
8. **描画とロジックの密結合**: 例えば `cityStop()` はモーダルHTML組み立て・DOM操作・効果音再生・ログ出力・状態変更を1関数内で行っており、ロジックだけを再利用・テストすることができない。

## 5. Clean Architecture / DDD / TDD が効く理由

| 課題 | 対応する設計方針 |
|---|---|
| 保守性/責務の混在 | Clean Architecture の層分離(Domain / Application / Infrastructure / Presentation) |
| トークン消費過大 | ドメイン単位でファイルを小分割(目安200〜300行)。1タスクに必要な文脈だけをLLMに渡せるようにする |
| テスト皆無・型なし | TypeScript化 + ドメイン層のTDD、ユースケース単位のユニットテスト |
| グローバル状態管理 | `GameSession` 集約に状態を集約し、アプリケーション層のユースケース経由でのみ変更 |
| コンテンツとコードの同居 | コンテンツを JSON データパック化し、`CountryContentRepository` 経由で読み込む(コードとデータを分離) |
| 翻訳文字列の保守性 | `next-intl` 等によるロケールJSONファイル化 |
| 描画とロジックの密結合 | ドメインイベント(例: `PropertyPurchased`, `SpiritStruck`)を発行し、ログ・音声・演出は購読側(Presentation/Infrastructure)に分離 |

この後の章で、上記方針を具体的なアーキテクチャ・ドメインモデル・フォルダ構成・テスト戦略に落とし込みます。
